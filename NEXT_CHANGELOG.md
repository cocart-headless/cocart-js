# Next Changelog for CoCart SDK <!-- omit in toc -->

> [!WARNING]
> This changelog is **NOT** final. It lists the changes waiting for the next release of `@cocartheadless/sdk`, `@cocartheadless/checkout`, `@cocartheadless/analytics-gtm` and `@cocartheadless/analytics-datafast`, to be moved into each package's `CHANGELOG.md` under the new version when it's released.

## Changed

- **Retries never send a change twice.** With `maxRetries` set, a request that changes something (a POST, PUT or DELETE: placing an order, paying, adding to the cart) is no longer sent again after a timeout or a dropped connection, as it may already have run on the store: a retried checkout could charge the card twice. A 429 is still retried for any request, since the rate limit refuses it before it runs, and a 503 or timeout for a GET.
- **Response types now match what CoCart actually returns.** The types for carts, products, variations, categories, the store and sessions (`CartResponse`, `CartItem`, `Product`, `ProductVariation`, `StoreInfo`, `SessionItem`…) were written by hand and didn't match the API. For example, they had unprefixed customer address fields, `shipping` as an array, image `src` as a string, and product attributes as an array. They're now generated from the CoCart OpenAPI spec, which is checked against live responses (`npm run generate:types`). The export names are the same, but the shapes have changed, so code that relied on the old (wrong) shapes may now show type errors. The types also reflect how CoCart sends data: amounts are minor-unit strings, and empty maps (`notices`, `price_range`, `attributes`…) are `{}` since CoCart Starter 5 (CoCart 4.x sent `[]`, which the `Response` helpers still accept). New exports: `CoCartSchemas`, `CartBillingAddress`, `CartShippingAddress`, `CartShipping`, `CartTotalsBreakdown` (the `GET /cart/totals` breakdown), `CartTax`, `ProductAttributeDetail`, `ProductVariationSummary`, `ProductCategoryDetail`. `CartItemImage` and `CustomerAddress` are deprecated.
- **`Response.getNotices()` returns notices keyed by type** (`{ success: [...], error: [...] }`), which is how CoCart sends them, instead of a list. When there are none it returns `{}`.
- **A browser client remembers the cart on its own.** The client now reads the cart key from `localStorage` or cookies (`LocalStorage`, `CookieStorage`, `MemoryStorage`) when it's created. Before, a page reload started a new cart unless you called `restoreSession()`. You still need `await restoreSession()` with `EncryptedStorage`.
- **A guest cart that no longer exists is replaced automatically.** CoCart Starter 5 refuses a cart key with no cart session on every cart route (`cocart_invalid_cart`), for example after the cart expired. The client then forgets the stored key and retries the request once as a new guest, so the shopper isn't stuck.
- **The account types match what CoCart Plus 2.0 returns.** `AccountProfile`, `AccountOrderDetail`, `AccountOrdersResponse`, `AccountOrderSummary`, `AccountDownload`, `AccountCancelOrderResult`, `RegisteredCustomer` and `AccountSubscriptionPaymentMethodResult` were written by hand and are now generated from the CoCart Plus spec (`npm run generate:types`), so their shapes have changed: the profile's details are at the top (`first_name`, `stats.orders_count`), not under `user` (`AccountUser` is deprecated); an order has `id`, `number`, `key` and `status.code`; downloads come as a list. Every response document says what it is in `object`, and a request that changes something says what it did in `result` (`code`, `message`). The fields of `AccountUpdateInput` are optional: send only what changes.
- **A 409, 429 or 5xx is never a `ValidationError`.** It was when its code contained `invalid` or `missing` (`cocart_order_invalid_status` is a 409); it's now a `CoCartError`. A 400 is still a `ValidationError` and a 401 or 403 an `AuthenticationError`.
- **`requestRaw()`, which every CoCart Plus route uses, now emits `request`, `response` and `error` events and shows in the debug output**, like the other requests, and its error messages name the route (`POST /cocart/v2/checkout: … [code]`). It still never sends a request again. The `response` event now carries the `response`.
- **`mainPlugin` `'basic'` is renamed `'starter'`**, after the CoCart Starter plugin. It's the default and what `getMainPlugin()` returns. `requiresBasic()` is renamed `requiresStarter()`, and the `version.requiresBasic` message key is renamed `version.requiresStarter`. A new `MainPlugin` type is exported.

## Added

- `CookieStorage` keeps the cart key in a cookie, so a server render can show the same cart as the browser. The framework adapters' `createServerClient()` reads that cookie when there's no `X-Cart-Key` header.
- `Response.getShipping()` returns the cart's whole `shipping` field: the package count, whether shipping has been calculated, and the packages.
- Methods for the CoCart Plus 2.0 routes the SDK didn't cover: `cart().getMini()`, `cart().removeCoupons()`, `cart().removeAllItems()` (keeps coupons and fees), `products().shippingRates()`, `products().createReview()`, and on `account()`: `updateAddress()`, `cancelOrder()`, `verifyEmail()`, `sendOrderEmailVerification()`, `verifyOrderEmail()`, the subscription methods (`getSubscriptions()`, `getSubscription()`, `suspendSubscription()`, `reactivateSubscription()`, `cancelSubscription()`, `setSubscriptionAutoRenew()`, `updateSubscriptionPaymentMethod()`, `resubscribe()`, `cancelResubscribe()`) and `requestOrderWithdrawal()`.
- `applyCoupon()` and `checkCoupons()` take an optional email for coupons restricted to certain emails; `addFee()` takes an optional tax class.
- Account (CoCart Plus 2.0): `getOrders()` filters by `status` (one or a list), by date with `after` and `before`, and by `subscription_order_type`; `getSubscriptions()` filters by `status`; both return `pagination`. `getProfile()`, `getOrder()`, `getGuestOrder()` and `getSubscription()` take `formatted` and `meta_keys`. The CoCart Plus documents are exported as types: `Order`, `OrderList`, `OrderUpdate`, `OrderPayment`, `Subscription`, `SubscriptionList`, `SubscriptionUpdate`, `SubscriptionPaymentMethodChange`, `Downloads`, `MiniCart`, `CartCoupons`, `ProductShippingRates`, `EmailChange`, `EmailVerification`, `OrderWithdrawal`, with every schema in `CoCartPlusSchemas` and `CoCartPlusCheckoutSchemas`.
- `CoCartError.getFields()` gives every field at fault, by path (`billing.postcode`), with its message: CoCart Plus checks a whole form at once. `getField()` gives the first, and `getReason()` the underlying plugin's own reason.
- `Response.getRateLimit()` reads the `RateLimit-*` headers.
- **Typed extension data.** `extensions` on the cart, cart items and products is typed for the plugins CoCart Plus supports (subscriptions, bundles, bookings, add-ons, warranty and more), `Response.getExtensions()` reads the cart's, and `CartExtensions`, `CartItemExtensions` and `ProductExtensions` can be augmented with any other plugin's data. See `docs/extension-data.md`.
- `CoCartError.getCart()` returns the cart sent with an error: `cocart_item_not_in_cart` carries the current cart since CoCart Starter 5.
- **Choices for CoCart Plus's supported plugins.** `addItem()` takes typed options (`AddItemOptions`), including a subscription plan (`convert_to_sub`), a gift recipient (`recipient_email`) and a warranty (`item_data.warranty`). `cart().changePlan(itemKey, value)` switches a cart item to another plan, or to one-time. A product's plan options no longer have `selected`, since nothing is chosen before the cart; a cart item's options (`CartItemSubscriptionSchemeOption`) still mark the current one.
- Checkout: `confirmReturn()` and `confirmOrderPayment()` finish a payment when the customer comes back from an off-site step, such as a Stripe 3D Secure page (CoCart Plus 2.0). They send the order key in the body, not the URL. `submit()` returns `redirectUrl` for those steps instead of retrying, and the final `CheckoutResult` as `result`. With `createStripeGateway()`, `submit()` also takes Cash App Pay, WeChat Pay and Boleto/OXXO/Multibanco voucher payments for an order placed on hold, without retrying: Stripe's webhook marks the order paid. If the customer doesn't finish, it throws `checkout_payment_not_completed` with the unpaid order's ID and key.
- Checkout: `submit()` won't take payment when the checkout's total has changed since the app last got it from `getCheckout()` or `updateCheckout()`, for example because its own update chose a dearer shipping method: it throws `409 cocart_checkout_total_mismatch`, as CoCart Plus does, with the new checkout in `data.checkout` to show. The next `submit()` goes ahead.
- Checkout: a failed payment's `result.error` is typed (`PaymentError`, `PaymentErrorCode`): a stable `code` such as `card_declined` or `incorrect_cvc` to branch on, plus the gateway's own code and message (CoCart Plus 2.0).
- **Checkout: `placeOrder()` and `CheckoutResult`.** `placeOrder()` creates the order and takes payment, with `payment_data` as a map of the keys the gateway reads (`{ 'wc-stripe-payment-method': 'pm_…' }`); a free order needs neither `payment_data` nor `payment_method`. It returns a `CheckoutResult`, read from the order CoCart Plus 2.0 returns with what the payment did in `result`: `code` (`order_placed`, `action_required`, `payment_pending`, `payment_failed`, or `payment_method_changed` for a subscription; the type is `PaymentResultCode`), `isComplete`, `isAwaitingPayment` (the order is placed and the customer still pays: Cash App Pay, WeChat Pay, Stripe vouchers, BLIK, a Multibanco voucher), `needsConfirmation`, `needsRedirect`, `isPending`, `isFailed`, the order's `orderId`, `orderKey`, `orderNumber` and `orderStatus` (or `subscriptionId`), `clientSecret`, `paymentMethodType`, `message` and `errorCode`. A declined card is a result to read, not an exception. `payForOrder()`, `confirmReturn()` and `account().updateSubscriptionPaymentMethod()` return the same result. `payForOrder()` sends the order key in the body, not the URL.
- Checkout: `getSavedPaymentMethods()` lists a logged-in customer's saved payment methods (`id`, `gatewayId`, `label` such as "Visa ending in 4242", `type`, `expires`, `isDefault`), for every gateway or one, with whether the gateway can charge subscription renewals (`supportsSubscriptions`). Pay with one as `wc-{gateway}-payment-token` in `payment_data`.
- `account().updateSubscriptionPaymentMethod()` takes a new card in `payment_data` as well as a saved card's `token_id`, and returns a `CheckoutResult`, since a new card may need 3D Secure: `isComplete` once the change went through (`payment_method_changed`, with `subscriptionId`). `AccountSubscriptionPaymentMethodResult` types its response: the subscription.
- Checkout: shared test fixtures (`packages/checkout/tests/fixtures/`), the request and response data every CoCart SDK replays to test its checkout the same way. They cover every way a payment can end: placed, awaiting payment, needing confirmation or a redirect, pending, failed, refused because another payment is running or the total changed, and how a lost checkout ended.
- **Checkout: finding out how an order ended when no answer came back.** `placeOrder()` sends each order with a random `checkout_id` (or yours, in the input: 16 to 64 letters, digits, `-` or `_`, or it's refused before sending with `checkout_invalid_checkout_id`). When the connection drops, the request times out, a proxy gives up waiting, or another request is still taking payment for the cart (`409 cocart_payment_in_progress`), it throws `CheckoutOutcomeUnknownError` with that `checkoutId`, and `getCheckoutStatus(checkoutId)` asks CoCart Plus 2.0 how it ended: its `code` is `order_placed`, `payment_required` (pay it with `payForOrder()`), `in_progress` (ask again) or `not_placed` (place it again), with a `message` and, once there is an order, `orderId`, `orderKey`, `orderNumber` and `orderStatus`. `CheckoutOutcomeUnknownError` is a `CoCartError` and keeps the original codes.
- Checkout: `CheckoutConfig.order_received_url`, where gateways send the customer back after an off-site step, `address_autocomplete` (whether address search works, and its providers), and the terms text with its links (`store.terms_text`, `terms_links`, `terms_url`, `privacy_url`) (CoCart Plus 2.0).
- Checkout: `getCheckout()` takes `currency`, `formatted` and `thumb`, and `getOrderReceived()` takes `formatted` and `meta_keys`. `updateCheckout()` returns the checkout with what it did in `result`: `checkout_updated`, or `checkout_partly_updated` with what wasn't applied, and why, in `result.not_applied`. `applyCoupon()` and `removeCoupon()` on the checkout client go through `PUT /checkout` and return the checkout with its new totals; `getShippingMethods()` returns the checkout's own shipping packages, with their rates as a list; `getOrderSummary()` also returns the total lines to display. The checkout package's types (`CheckoutState`, `CheckoutConfig`, `OrderReceived`, `CheckoutPaymentMethodsResponse`…) are generated from the CoCart Plus 2.0 checkout spec.

## Fixed

- **`Response.getShippingMethods()` always returned an empty list on a real store.** CoCart sends shipping packages keyed by package ID under `shipping.packages`, and the SDK expected a plain array. It now returns the packages.
- **`applyCoupon()` was rejected by CoCart Plus** because it sent the code as `coupon` instead of `code`.
- **`addFee()` was rejected by CoCart Plus** because it sent the amount as a number; the route takes a string.
- **`Response.getFees()` returned the fees object instead of a list.** CoCart keys cart fees by fee ID; `getFees()` now returns them as a list.
- **`account().changePassword()`, `getOrderDownloads()`, `getGuestOrderDownloads()` and `getReviews()` called routes CoCart Plus doesn't have.** The password now goes to `POST /my-account` (only the password fields), order downloads come from `GET /my-account/orders/{id}/downloads` (with the billing email for a guest), and reviews come from `products/reviews/mine`.
- **`removeCoupon()` broke for coupon codes with spaces, `%`, `#` or `?`.** The code went into the URL unencoded. It's now encoded.
- **`ProductOrderBy` allowed `'price'`, which CoCart rejects.** It now lists the sort orders CoCart accepts: sort by price with `price_asc` or `price_desc`. `menu_order`, `name`, `alphabetical`, `reverse_alpha`, `sales`, `review_count`, `by_stock`, `on_sale_first` and `featured_first` were missing, and `relevance` and `rand` work with CoCart Starter.
- **Error messages included the full request URL**, which can contain the cart key and API credentials. They now name only the route.
- **The debug output printed full request URLs**, with the cart key, an order key, a guest's email or an email verification key in the query string. Every query value now shows as `***`.
- **With `maxRetries`, a rate-limited request was retried too soon.** CoCart Plus says how long to wait in `RateLimit-Retry-After`, which the SDK didn't read, so it retried after a second or two and hit the limit again. It now waits as long as the store says (at most 60 seconds), and still reads `Retry-After` from a proxy.
- **The ETag cache kept responses the store marks private.** Checkout, order and account responses are sent with `Cache-Control: no-store, private`; the client no longer keeps them in memory.
- **analytics-gtm and analytics-datafast sent full request URLs to the analytics service**, with the cart key, an order key or an email address in the query string. They now send the route only. They also counted refused requests (a 400 on add-to-cart was an `add_to_cart`), and fire `purchase` only when a checkout, payment or payment confirmation places the order (`result.code` `order_placed`), with the order as `transaction_id` and its `value`: a declined card or a 3D Secure step is a 200 too, and checkouts placed with `@cocartheadless/checkout` sent no events at all.
- **The default Stripe `tokenize` failed when the Payment Element hides its own billing fields.** It now calls `elements.submit()` first and sends the checkout's billing address to Stripe. This applies to `createStripeGateway()` and `createWooPaymentsGateway()`.
